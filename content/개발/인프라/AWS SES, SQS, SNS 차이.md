> 이메일을 보내고 싶으면 SES, 여러 곳에 동시에 알리고 싶으면 SNS, 처리 순서를 보장하며 줄 세우고 싶으면 SQS. 셋 다 "메시지를 전달한다"는 공통점이 있지만 해결하는 문제가 다르다.

---

## 먼저 큰 그림을 보자

서비스가 커지면 "A에서 뭔가 일어났을 때 B가 반응해야 하는" 상황이 생긴다. 사용자가 가입하면 환영 이메일을 보내고, 주문이 들어오면 결제·재고·배송 시스템이 동시에 알아야 하고, 이미지가 업로드되면 리사이징 작업이 큐에 쌓여야 한다.

이 세 가지 상황에 각각 맞는 AWS 서비스가 있다:

```
"이메일을 보내야 해"           → SES (Simple Email Service)
"한 이벤트를 여러 곳이 알아야 해" → SNS (Simple Notification Service)
"작업을 줄 세워서 처리해야 해"   → SQS (Simple Queue Service)
```

---

## SES — 이메일을 보내고 받는 우체국

SES는 이메일 전문 서비스다. 대량 이메일을 안정적으로 보내는 게 핵심 역할이다.

직접 SMTP 서버를 운영하면 IP가 스팸 블랙리스트에 올라가거나, 반송 처리를 직접 해야 하는 등 골치가 아프다. SES는 이런 문제를 대신 처리해준다.

```
앱 서버 → SES → 사용자 메일함
                ├─ 인증 확인 (SPF, DKIM, DMARC)
                ├─ 반송(bounce) 자동 처리
                └─ 스팸 평판 관리
```

SES는 보내기만 하는 게 아니라 **받기도** 된다. 수신한 이메일을 Lambda로 처리하거나, S3에 저장하거나, SNS로 알림을 보낼 수 있다.

처음 생성하면 **샌드박스 모드**로 시작한다. 인증된 이메일 주소로만 보낼 수 있고, 일일 전송량도 제한된다. 대량 발송하려면 AWS에 샌드박스 해제를 요청해야 한다. 이건 스팸 발송을 막기 위한 장치다.

**SES를 쓰는 상황:** 회원가입 인증 메일, 비밀번호 재설정, 마케팅 뉴스레터, 주문 확인 메일 등 이메일이 필요한 모든 곳.

---

## SNS — 한 마디 외치면 구독자 전원이 듣는 확성기

SNS는 **Pub/Sub(발행/구독)** 모델의 메시징 서비스다. 하나의 메시지를 여러 수신자에게 동시에 전달한다.

작동 방식은 라디오 방송과 비슷하다:

```
발행자(Publisher)
  │
  ▼
토픽(Topic) = "주문 생성됨"
  │
  ├─ 구독자 1: Lambda (이메일 발송)
  ├─ 구독자 2: SQS (재고 차감 큐)
  ├─ 구독자 3: HTTPS (외부 웹훅)
  └─ 구독자 4: SMS (관리자 문자)
```

발행자는 토픽에 메시지를 던지기만 한다. 누가 구독하고 있는지 알 필요 없다. 구독자를 추가하거나 빼도 발행자 코드는 바뀌지 않는다. 이 느슨한 결합이 핵심이다.

다양한 프로토콜로 전달할 수 있다:
- **Lambda** — 서버리스 함수 실행
- **SQS** — 큐에 메시지 넣기
- **HTTPS** — 외부 서비스에 웹훅
- **이메일** — 간단한 알림용 (대량 발송은 SES가 적합)
- **SMS** — 문자 메시지

**SNS를 쓰는 상황:** 하나의 이벤트가 발생했을 때 여러 시스템이 동시에 반응해야 하는 경우. 주문 생성 → 결제+재고+알림이 동시에 돌아가야 할 때.

## SQS — 작업을 줄 세워서 하나씩 처리하는 대기열

SQS는 **메시지 큐**다. 메시지를 넣으면 소비자가 꺼내서 처리한다. SNS가 "동시에 여러 곳에 알리기"라면, SQS는 "순서대로 줄 세워서 처리하기"다.

```
생산자 → [ 메시지1 | 메시지2 | 메시지3 ] → 소비자
         ────────── 큐 ──────────
```

핵심은 **생산 속도와 소비 속도를 분리**하는 것이다. 이미지 업로드가 초당 100건이 들어와도 리사이징 서버가 초당 10건만 처리할 수 있으면, 나머지 90건은 큐에서 기다린다. 큐가 없으면 리사이징 서버가 과부하로 죽는다.

두 가지 타입이 있다:

```
Standard Queue         FIFO Queue
──────────────         ──────────
최소 1번 전달 보장       정확히 1번 전달
순서 보장 안 됨          순서 보장됨
처리량 거의 무제한       초당 300건 (배치 시 3000건)
```

Standard Queue는 같은 메시지가 2번 전달될 수 있다(at-least-once). 소비자 쪽에서 중복 처리를 대비해야 한다. FIFO Queue는 정확히 1번, 순서대로 전달하지만 처리량이 제한된다.

메시지를 꺼내면 즉시 삭제되는 게 아니라 **visibility timeout** 동안 다른 소비자에게 안 보인다. 처리가 끝나면 소비자가 직접 삭제한다. 처리 중에 소비자가 죽으면 timeout 후 메시지가 다시 나타나서 다른 소비자가 처리한다.

```
소비자가 메시지 꺼냄 → 30초간 다른 소비자에게 안 보임
  ├─ 처리 성공 → 소비자가 삭제 요청 → 큐에서 제거
  └─ 처리 실패 (소비자 죽음) → 30초 후 다시 나타남 → 다른 소비자가 재처리
```

**SQS를 쓰는 상황:** 작업을 비동기로 처리하고 싶을 때. 이미지 리사이징, 이메일 발송 큐, 로그 처리, 주문 후속 처리 등.

---

## 셋을 조합하면 이런 구조가 된다

실제로는 이 서비스들을 조합해서 쓰는 경우가 많다:

```
사용자가 주문
  │
  ▼
API 서버 → SNS 토픽 "주문 생성됨"에 발행
              │
              ├─ SQS (결제 큐) → 결제 서비스가 꺼내서 처리
              ├─ SQS (재고 큐) → 재고 서비스가 꺼내서 처리
              └─ Lambda → SES로 주문 확인 이메일 발송
```

SNS가 이벤트를 팬아웃(fan-out)하고, 각 구독자는 SQS를 통해 자기 속도에 맞게 처리한다. SNS + SQS 조합을 "팬아웃 패턴"이라고 부른다.

---

## 한눈에 비교

| | SES | SNS | SQS |
|---|---|---|---|
| 한 줄 요약 | 이메일 전문 | 이벤트 팬아웃 | 작업 대기열 |
| 비유 | 우체국 | 확성기 (라디오 방송) | 은행 번호표 |
| 방향 | 1:1 (발신자→수신자) | 1:N (토픽→구독자들) | 1:1 (큐→소비자) |
| 메시지 보관 | 안 함 | 안 함 (즉시 전달) | 최대 14일 보관 |
| 재시도 | 자체 재시도 (반송 처리) | 전달 실패 시 재시도 | visibility timeout 후 재노출 |
| 핵심 가치 | 이메일 인프라 관리 대행 | 서비스 간 느슨한 결합 | 생산/소비 속도 분리 |
