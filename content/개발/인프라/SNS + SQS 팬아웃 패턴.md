## 문제는 여기서 시작된다

쇼핑몰에서 주문이 하나 들어왔다고 하자. 이 주문 하나 때문에 뒤에서 벌어져야 하는 일이 여러 개다:

```
주문 생성됨 → 결제 처리
           → 재고 차감
           → 확인 이메일 발송
           → 배송 준비 요청
```

가장 단순한 방법은 API 서버가 이걸 순서대로 호출하는 거다:

```
API 서버
  │
  ├─ 1. 결제 서비스 호출 (200ms)
  ├─ 2. 재고 서비스 호출 (150ms)
  ├─ 3. 이메일 서비스 호출 (300ms)
  └─ 4. 배송 서비스 호출 (100ms)

  총 응답 시간: 750ms
```

동작은 하는데 문제가 세 가지 있다.

느리다. 4개를 순서대로 호출하니 응답 시간이 다 합쳐진다. 사용자는 750ms를 기다려야 "주문 완료" 화면을 봄.

하나가 죽으면 전부 멈춘다. 이메일 서비스가 장애면? 결제와 재고는 성공했는데 이메일에서 에러가 터지면서 전체가 실패한다. 이메일 때문에 주문이 안 되는 건 말이 안 됨.

코드가 엉킨다. API 서버가 결제·재고·이메일·배송 서비스를 전부 알고 있어야 한다. 나중에 "포인트 적립" 기능이 추가되면? API 서버 코드를 열어서 5번째 호출을 추가해야 한다. 서비스가 늘어날 때마다 API 서버가 뚱뚱해짐.

## 팬아웃은 부채꼴로 퍼뜨리는 것이다

팬아웃(fan-out)이란 말 자체가 "부채처럼 펼친다"는 뜻이다. 하나의 메시지를 여러 갈래로 동시에 퍼뜨리는 패턴.

카드 한 벌을 탁자 위에 부채꼴로 펼치는 장면을 떠올리면 된다. 한 손으로 밀면(하나의 이벤트) 카드가 여러 방향으로 퍼진다(여러 수신자에게 전달).

AWS에서는 SNS(토픽) + SQS(큐) 조합으로 이걸 구현한다:

```
API 서버
  │
  │  "주문 생성됨" 메시지 하나만 던진다
  ▼
SNS 토픽
  │
  │  토픽이 구독자 전원에게 동시에 복사해서 전달한다
  │
  ├─→ SQS (결제 큐)   → 결제 서비스
  ├─→ SQS (재고 큐)   → 재고 서비스
  ├─→ SQS (이메일 큐)  → 이메일 서비스
  └─→ SQS (배송 큐)   → 배송 서비스
```

API 서버는 SNS 토픽에 메시지 하나만 던지고 끝이다. 누가 듣고 있는지 모른다. 토픽이 알아서 구독자들에게 복사해서 전달함.

---

## 아까 세 가지 문제가 어떻게 풀리냐면

빨라진다. API 서버는 SNS에 메시지 하나만 보내면 끝이다. 결제·재고·이메일·배송은 각자 큐에서 꺼내서 동시에 처리한다.

```
전: API → 결제 → 재고 → 이메일 → 배송 (직렬, 750ms)
후: API → SNS (수십 ms) → 사용자에게 바로 응답
         ↓ (백그라운드에서 동시에)
         결제 / 재고 / 이메일 / 배송
```

하나가 죽어도 나머지는 돌아간다. 이메일 서비스가 죽으면? 이메일 큐에 메시지가 쌓여서 기다릴 뿐이다. 결제와 재고는 자기 큐에서 정상 처리. 이메일 서비스가 복구되면 밀린 메시지를 꺼내서 처리하면 됨. SQS가 최대 14일까지 메시지를 보관하니까 여유가 있다.

코드가 분리된다. "포인트 적립" 기능이 추가되면? SNS 토픽에 SQS 구독 하나만 추가하면 됨. API 서버 코드는 한 줄도 안 바뀐다.

```
SNS 토픽 "주문 생성됨"
  │
  ├─→ SQS (결제 큐)
  ├─→ SQS (재고 큐)
  ├─→ SQS (이메일 큐)
  ├─→ SQS (배송 큐)
  └─→ SQS (포인트 큐)  ← 이것만 추가. API 서버는 모른다.
```

## SNS만 쓰면 안 되나? 왜 SQS를 끼우나

SNS만으로도 Lambda나 HTTPS 엔드포인트에 직접 전달할 수 있다. 근데 중간에 SQS를 끼우는 이유가 있다.

속도 차이를 흡수한다. SNS는 메시지를 받는 즉시 구독자에게 푸시함. 만약 주문이 초당 1000건 들어오는데 결제 서비스가 초당 100건만 처리할 수 있으면? SNS가 직접 결제 서비스를 호출하면 900건이 실패한다. SQS가 중간에서 버퍼 역할을 하면 결제 서비스는 자기 속도에 맞게 큐에서 꺼내서 처리함.

```
SNS 직접 전달 (버퍼 없음):
  1000건/초 → 결제 서비스 (100건/초 처리 가능) → 900건 실패

SQS를 중간에 넣으면:
  1000건/초 → SQS 큐 (무제한 적재) → 결제 서비스 (100건/초로 꺼내감) → 실패 없음
```

재처리가 보장된다. SNS가 Lambda를 직접 호출했는데 Lambda가 에러를 뱉으면? SNS는 몇 번 재시도하고 포기한다. SQS를 끼우면 메시지가 큐에 남아 있으니 소비자가 복구된 후 다시 처리할 수 있음. 계속 실패하는 메시지는 Dead Letter Queue(DLQ)로 빠져서 나중에 원인을 분석할 수 있다.

```
처리 실패 흐름:

SQS 큐 → 소비자가 꺼냄 → 처리 실패
  ↑                          │
  └── visibility timeout 후 ──┘  (자동 재시도)

3번 연속 실패 → DLQ(Dead Letter Queue)로 이동 → 나중에 원인 분석
```

소비자를 독립적으로 스케일링한다. 결제 큐가 밀리면 결제 서비스 인스턴스를 늘리면 됨. 재고 큐는 여유로우면 인스턴스 하나로 충분. 각 큐의 깊이를 보고 서비스별로 독립적으로 오토스케일링할 수 있다.

## 주의할 점

메시지 순서가 보장되지 않는다. SNS Standard Topic + SQS Standard Queue 조합에서는 메시지가 보낸 순서대로 도착하지 않을 수 있음. "주문 생성 → 주문 취소"가 "주문 취소 → 주문 생성" 순서로 처리될 수 있다. 순서가 중요하면 FIFO Topic + FIFO Queue를 쓰되, 처리량 제한이 있다.

중복 전달이 일어날 수 있다. Standard Queue는 같은 메시지를 두 번 전달할 수 있다(at-least-once). 소비자는 같은 주문을 두 번 처리해도 결과가 같도록 멱등성을 보장해야 함. 결제 서비스는 주문 ID로 중복 결제를 막는 로직이 필요하다.

구독자가 많아지면 비용이 늘어난다. SNS에서 SQS로 전달할 때마다 SQS 요청 비용이 발생한다. 구독자가 10개면 메시지 하나당 SQS 요청 10번임. 구독자 수와 메시지 양을 곱해서 비용을 미리 계산해야 한다.

## 더 큰 그림에서 보면

팬아웃 패턴은 이벤트 드리븐 아키텍처의 기본 빌딩 블록이다. 서비스 간 통신을 직접 호출(동기)에서 이벤트 발행(비동기)으로 바꾸는 첫 번째 단계.

```
1단계: 직접 호출 (API → API) — 단순하지만 강하게 결합
2단계: 팬아웃 (SNS + SQS) — 느슨한 결합, 독립적 확장
3단계: 이벤트 소싱 / CQRS — 모든 상태 변화를 이벤트로 기록
4단계: EventBridge 같은 이벤트 버스 — 이벤트 라우팅 규칙이 복잡해질 때
```

서비스가 3-4개일 때는 직접 호출이 단순해서 좋다. 서비스가 늘어나면서 "이 이벤트를 누가 알아야 하지?"가 복잡해지면 팬아웃이 자연스러운 다음 단계임.
