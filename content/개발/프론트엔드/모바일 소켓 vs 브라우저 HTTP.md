> 모바일 앱은 서버와의 연결을 직접 열고, 데이터가 흐르는 걸 눈으로 보고, 문제가 생기면 어디서 막혔는지 안다. 웹 앱은 브라우저한테 "이거 좀 보내줘" 하고 맡기고, 결과만 돌려받는다. 같은 HTTP 요청인데 볼 수 있는 것이 다르다.

---

## 택배를 직접 가져가는 사람과 앱으로 시키는 사람

친구에게 물건을 보내야 한다.

**방법 1: 직접 차를 몰고 간다.** 집에서 출발하고, 고속도로에 올라가고, 톨게이트를 지나고, 친구 집 앞에 도착해서 초인종을 누른다. 이 과정의 모든 순간을 내가 직접 경험한다. 고속도로에서 막히면 "아, 여기서 막히는구나" 하고 안다. 친구가 문을 안 열면 "집에 없나?" 하고 안다. 어디서 문제가 생겨도 정확히 어느 단계인지 파악할 수 있다.

**방법 2: 택배를 보낸다.** 편의점에서 물건을 맡긴다. 그다음? 기다린다. 중간에 무슨 일이 일어나는지 모른다. 다음 날 친구가 "받았어"라고 하면 성공. "아직 안 왔는데?"라면 실패. 근데 왜 실패했는지 — 택배 분류 과정에서 빠졌는지, 배송 트럭이 고장났는지, 친구가 부재중이었는지 — 나는 알 수 없다.

**모바일 앱이 방법 1이고, 웹 앱이 방법 2다.**

---

## 소켓이 뭔지부터 — 두 컴퓨터를 잇는 파이프

내 앱이 서버에서 데이터를 받아오려면, 둘 사이에 데이터가 흐를 수 있는 통로가 필요하다. 이 통로를 **소켓(socket)**이라고 부른다.

수도 배관을 생각하면 된다. 수도꼭지(내 앱)와 정수장(서버) 사이에 파이프가 있어야 물이 흐른다. 소켓이 그 파이프다.

```
내 앱 ◄──────── 소켓 (파이프) ────────► 서버

     데이터가 이 파이프를 타고 오간다
```

파이프를 연결하려면 상대방 주소를 알아야 한다. 소켓에서는 **IP 주소**(건물 주소)와 **포트 번호**(건물 안의 방 번호)가 그 주소다. 웹 서버는 보통 443번 방에서 대기하고 있다.

---

## 파이프가 연결되기까지 — 세 번의 확인

수도관을 처음 연결하면 바로 물을 틀지 않는다. 수압 테스트를 한다. "물 보낸다?" → "어, 받을 준비 됐다" → "좋아, 시작하자." TCP도 똑같다. **3-way handshake** — 세 번 확인하고 나서야 데이터를 보내기 시작한다.

```
내 앱:  "연결해도 돼?"  ──────►  서버
내 앱:  ◄──────  "응, 준비됐어"  서버
내 앱:  "좋아, 시작하자"  ──────►  서버

     파이프 개통! 이제 데이터 전송 가능
```

이 다음에 HTTP 요청("유저 목록 줘")을 보내고, 서버가 응답("여기 있어")을 돌려주고, 끝나면 파이프를 닫는다.

```
파이프 연결 → 요청 보냄 → 서버가 처리 → 응답 헤더 도착 → 응답 바디 도착 → 파이프 닫음
──────────────────────────────────────────────────────────────────────────
① 연결 단계        ② 전송 단계          ③ 수신 단계
```

HTTP 요청 하나의 일생이 이렇게 세 단계를 거친다. 왜 이걸 알아야 하냐면 — **각 단계에서 터지는 문제의 원인이 전부 다르기 때문이다.**

- ① 연결 단계에서 터짐 → 서버가 죽었거나 주소가 틀림
- ② 전송 단계에서 터짐 → 보내는 데이터가 너무 크거나 네트워크 끊김
- ③ 수신 단계에서 터짐 → 서버 응답이 느리거나 데이터가 너무 큼

"타임아웃이 났다"만 알면 원인을 못 잡는다. **"어느 단계에서 타임아웃이 났는지"**를 알아야 디버깅 방향이 잡힌다.

---

## 모바일 앱은 파이프를 직접 깔고 직접 지켜본다

모바일 앱은 운영체제의 소켓 API를 직접 쓴다. 아까 비유로 말하면 **직접 차를 몰고 가는 사람**이다. 파이프의 모든 단계를 코드가 직접 경험한다.

```
모바일 앱이 보는 것:

  "파이프 연결 시작했다"           ← ① 연결 시작 (눈으로 봄)
  "서버가 응답했다, 연결 성공"      ← ① 연결 완료 (눈으로 봄)
  "요청 데이터를 보내는 중이다"     ← ② 전송 중 (눈으로 봄)
  "서버가 응답 헤더를 보내왔다"     ← ③ 수신 시작 (눈으로 봄)
  "바디 데이터가 들어오고 있다"     ← ③ 수신 중 (눈으로 봄)
  "다 받았다"                    ← ③ 수신 완료 (눈으로 봄)
```

모든 단계가 보이니까, 각 단계에 독립적인 타이머를 걸 수 있다:

```
연결 타이머: 5초    ← 5초 안에 파이프가 안 열리면 → "서버 연결 실패"
전송 타이머: 10초   ← 10초 안에 요청이 안 보내지면 → "전송 실패"
수신 타이머: 30초   ← 30초 동안 데이터가 안 오면 → "수신 시간 초과"
```

5초 만에 연결이 안 되면 "서버가 죽었나 보다"라고 바로 판단할 수 있다. 연결은 됐는데 데이터가 안 오면 "서버가 응답을 만드는 데 오래 걸리나 보다"라고 다른 판단을 내린다.

---

## 웹 앱은 브라우저에게 맡기고 밖에서 기다린다

웹 앱은 **택배를 맡기는 사람**이다. 브라우저라는 택배 회사에 요청을 맡기고, 결과만 돌려받는다.

JavaScript 코드는 소켓을 만들 수 없다. 브라우저가 제공하는 API(`fetch`, `XMLHttpRequest`)를 통해서만 요청을 보낸다. 브라우저가 내부적으로 파이프를 열고, 데이터를 주고받고, 결과를 JavaScript에 전달한다.

```
웹 앱이 보는 것:

  "요청 보냈다" (fetch 호출)
  ... (아무것도 안 보임. 브라우저가 내부적으로 처리 중) ...
  "결과 왔다" (Promise 이행)

  ──── 끝 ────
```

중간에 뭐가 일어나는지 모른다. 파이프가 언제 열렸는지, 헤더가 언제 도착했는지, 바디가 얼마나 왔는지 — 브라우저가 다 감추고 최종 결과만 준다.

타이머도 하나뿐이다:

```
모바일:                            웹:
  연결 타이머: 5초                    타이머: 30초 (종류 구분 없음)
  전송 타이머: 10초                   "시간 초과" ← 연결 때문? 수신 때문? 모름
  수신 타이머: 30초

  "연결에서 터졌네" (정확)             "뭔가 터졌네" (모호)
```

---

## 왜 브라우저는 이렇게 막아놨나

이게 의도적인 설계라는 걸 이해하면 납득이 된다.

모바일 앱은 사용자가 직접 골라서 설치한다. 앱스토어에서 심사도 받았다. 그래서 운영체제가 "이 앱은 믿을 만하니까 소켓을 써도 돼"라고 허용한다.

웹은 다르다. 링크를 하나 클릭하면 그 사이트의 코드가 바로 내 브라우저에서 실행된다. 설치도 없고 심사도 없다. 만약 이 코드가 소켓을 자유롭게 열 수 있으면?

```
evil.com의 코드가 내 브라우저에서 실행됨
  │
  ├─ 소켓으로 192.168.1.1 접속 → 내 공유기 해킹 시도
  ├─ 소켓으로 10.0.0.5:3306 접속 → 회사 DB 접근 시도
  └─ 소켓으로 localhost:6379 접속 → 내 PC의 Redis 탈취

  아무 사이트나 열었을 뿐인데 내 네트워크가 뚫린다
```

그래서 브라우저는 JavaScript에게 소켓을 주지 않는다. HTTP 요청만 허용하고, 그마저도 **Same-Origin Policy**와 **CORS**로 통제한다.

```
모바일: 사용자가 설치 → 심사 통과 → 신뢰됨 → 소켓 허용
웹:    링크 클릭만으로 실행 → 심사 없음 → 못 믿음 → 소켓 차단
```

## 이 차이가 실제로 만드는 문제

같은 HTTP 클라이언트 라이브러리를 쓰는데, 모바일에서는 타임아웃 종류가 정확하게 나오고, 웹에서는 엉뚱한 타입으로 나온다. 왜?

모바일에서는 파이프의 모든 단계가 보이니까 "연결 단계에서 터졌다 / 수신 단계에서 터졌다"를 정확히 구분한다. 웹에서는 브라우저가 중간 과정을 감추니까 라이브러리가 **추측**할 수밖에 없다.

```
서버가 응답 헤더는 보냈는데 바디를 늦게 보내는 상황:

모바일:
  파이프 열림 ✓ → 헤더 도착 ✓ → 바디 안 옴... → receiveTimeout (정확!)

웹:
  fetch 호출 → ... (내부 상황 안 보임) ... → 타임아웃
  라이브러리: "타이머가 아직 살아있으니 연결 문제인가?"
  → connectionTimeout (틀림! 연결은 됐는데)
```

이게 바로 [[Dio #2421 — Inaccurate Timeout Type Detection 학습 노트]]에서 다룬 버그다. 웹 어댑터가 XHR의 `readyState`라는 간접 단서로 타임아웃 종류를 추론해야 하는데, 그 추론 로직에 빈틈이 있었던 것이다.

---

## Flutter 개발자가 이걸 아는 게 뭐가 다른가

이 지식이 실제 Flutter 코드에서 어떻게 쓰이는지 보자.

### 타임아웃을 세 개로 나눠서 건다

Dio를 쓸 때 타임아웃을 하나만 거는 경우가 많다. 하지만 모바일에서는 세 단계를 각각 감시할 수 있으니, 각각 다른 값을 걸어야 의미가 있다.

```dart
final dio = Dio(BaseOptions(
  connectTimeout: Duration(seconds: 5),   // 파이프 여는 데 5초면 서버가 죽은 거다
  sendTimeout: Duration(seconds: 10),     // 요청 보내는 데 10초면 네트워크 문제다
  receiveTimeout: Duration(seconds: 30),  // 응답 받는 건 넉넉하게 (큰 데이터 대비)
));
```

왜 이렇게 나누냐면, 각 타임아웃에 대한 **대응이 다르기 때문이다**:

```
connectTimeout 발생 → 서버가 죽었거나 네트워크 끊김
  → 사용자에게: "서버에 연결할 수 없습니다"
  → 재시도: 잠시 후 1~2번만 (서버가 죽었으면 재시도해봤자 소용없다)

receiveTimeout 발생 → 서버가 느리거나 응답이 큼
  → 사용자에게: "응답 시간이 초과되었습니다"
  → 재시도: 바로 한 번 더 시도해볼 만하다 (일시적 과부하일 수 있다)
```

하나로 퉁치면 "타임아웃 났다"밖에 모르니까 사용자에게도 "뭔가 문제가 생겼습니다"라는 쓸모없는 메시지만 보여줄 수 있다.

### 에러 타입별로 다르게 처리한다

Dio의 `DioException`은 타입을 알려준다. 이걸 활용하면 에러 화면을 구체적으로 만들 수 있다.

```dart
try {
  final response = await dio.get('/users');
} on DioException catch (e) {
  switch (e.type) {
    case DioExceptionType.connectionTimeout:
      // 파이프가 안 열렸다 → 서버나 네트워크 문제
      showError('서버에 연결할 수 없습니다. 네트워크를 확인해주세요.');
    case DioExceptionType.receiveTimeout:
      // 파이프는 열렸는데 데이터가 안 온다 → 서버가 느리다
      showError('서버 응답이 느립니다. 잠시 후 다시 시도해주세요.');
    case DioExceptionType.connectionError:
      // 아예 네트워크가 없다 → 비행기 모드, 와이파이 끊김
      showError('인터넷 연결을 확인해주세요.');
    default:
      showError('요청 중 문제가 발생했습니다.');
  }
}
```

"뭔가 문제가 생겼습니다"와 "인터넷 연결을 확인해주세요"는 사용자 입장에서 완전히 다른 정보다. 소켓의 어느 단계에서 터졌는지를 아니까 이런 구분이 가능한 것이다.

### Flutter 웹 빌드에서는 에러 처리가 달라진다는 걸 안다

같은 Dio 코드를 `flutter build web`으로 빌드하면, 타임아웃 타입이 부정확할 수 있다는 걸 이제 안다. 웹에서는 `connectionTimeout`이라고 보고해도 실제로는 수신 단계에서 터진 것일 수 있다.

```dart
// 웹까지 고려한 에러 처리
on DioException catch (e) {
  if (kIsWeb) {
    // 웹에서는 타임아웃 종류 구분이 부정확할 수 있다
    // → connectionTimeout과 receiveTimeout을 묶어서 처리
    if (e.type == DioExceptionType.connectionTimeout ||
        e.type == DioExceptionType.receiveTimeout) {
      showError('요청 시간이 초과되었습니다.');
    }
  } else {
    // 모바일에서는 타입을 신뢰할 수 있다
    // → 각각 다른 메시지 표시
  }
}
```

이걸 모르면 "모바일에서는 잘 되는데 웹에서 에러 메시지가 이상하다"는 버그 리포트를 받고 헤맨다. 파이프가 보이느냐 안 보이느냐의 차이를 알면, 웹에서 왜 부정확한지 바로 납득이 되고 플랫폼별 분기가 자연스럽다.

### 재시도 전략을 타임아웃 타입에 따라 바꾼다

Dio 인터셉터에서 재시도 로직을 넣을 때, 무조건 재시도하는 게 아니라 타입별로 전략을 다르게 가져간다.

```dart
class RetryInterceptor extends Interceptor {
  @override
  void onError(DioException err, ErrorInterceptorHandler handler) {
    switch (err.type) {
      case DioExceptionType.connectionTimeout:
        // 서버가 죽었을 확률 높음 → 3초 대기 후 1번만 재시도
        _retryAfter(err, handler, delay: Duration(seconds: 3), maxRetries: 1);
      case DioExceptionType.receiveTimeout:
        // 일시적 과부하일 수 있음 → 바로 1번 재시도
        _retryAfter(err, handler, delay: Duration.zero, maxRetries: 1);
      case DioExceptionType.connectionError:
        // 네트워크 자체가 없음 → 재시도 의미 없음, 바로 에러 반환
        handler.next(err);
      default:
        handler.next(err);
    }
  }
}
```

연결 자체가 안 되는데 바로 재시도하면 똑같이 실패한다. 잠깐 기다렸다가 시도하는 게 낫다. 반면 수신 타임아웃은 서버가 일시적으로 바빴을 수 있으니 바로 다시 시도하는 게 합리적이다. **파이프의 어느 지점이 막혔는지에 따라 뚫는 방법이 다르다.**

---

## 한 장면으로 기억하기

```
모바일 = 직접 운전
  출발 → 고속도로 → 톨게이트 → 도착
  매 순간 어디인지 안다. 막히면 어디서 막히는지 안다.

웹 = 택배
  접수 → ... → 배송 완료
  중간 과정을 모른다. 문제가 생기면 "어딘가에서 문제" 밖에 모른다.
```
